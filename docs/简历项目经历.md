## 一、标准版（约 12 行，一页简历推荐）

**项目描述**
面向培训机构的教学管理系统后端，覆盖部门、员工、班级、学员、统计报表与操作日志六大模块，共 30 个 REST 接口、7 张表。采用 Spring Boot + MyBatis 三层架构，为管理端提供统一的鉴权、分页查询与审计能力。

**主要工作**

- 独立完成 **部门 / 员工 / 班级 / 学员** 四大模块的 CRUD 与分页查询，基于 MyBatis 动态 SQL（`<if>` / `<where>` / `<set>` / `<foreach>`）实现多条件组合检索，一套 Mapper 覆盖姓名模糊、性别、入职时间区间等可选筛选条件，避免为每种组合手写 SQL。
- 设计 **员工—工作经历一对多** 的数据装配：用嵌套 `resultMap` + `<collection>` 一次 JOIN 查询完成主从表映射，消除「查员工再循环查经历」的 N+1 问题；新增/修改时用 `foreach` 批量插入，将 N 次数据库往返合并为 1 次。
- 基于 **JWT + HandlerInterceptor + ThreadLocal** 实现无状态登录鉴权：登录签发含用户 ID 的 token，拦截器统一校验并注入当前登录人，`afterCompletion` 中强制清理 ThreadLocal，规避线程池复用导致的用户身份串号；未携带或非法 token 统一返回 401。
- 基于 **Spring AOP + 自定义注解** 实现操作审计：环绕通知记录操作人、类名、方法名、请求参数、返回值与耗时；序列化前过滤 `ServletRequest` / `MultipartFile` 等不可序列化参数，超长内容按 2000 字符截断，日志写入失败降级捕获、不影响主业务。
- 基于 **阿里云 OSS** 实现头像上传：将上传能力封装为独立组件，参数用 `@ConfigurationProperties` 绑定，访问凭证走环境变量而非硬编码，客户端句柄用 try-with-resources 释放；文件名采用 UUID + 日期分目录，规避重名覆盖。
- 设计 **统一响应与异常处理**：`Result{code,msg,data}` + `PageResult<T>{total,rows}` 静态工厂，配合 `@RestControllerAdvice` 全局兜底，并针对唯一键冲突单独处理为「xxx 已存在」的业务提示，避免把 500 堆栈暴露给前端。
- 排查并修复多类线上隐患：员工密码随 `select *` 返回前端、员工更新跨表操作缺少事务导致工作经历丢数据、日志写入与业务共用事务导致回滚时审计记录一并丢失等，补充了删除前的关联校验（部门下有员工 / 班级下有学员时禁止删除）。

**技术收获**：理解了事务传播行为（`REQUIRED` vs `REQUIRES_NEW`）在「业务 + 审计日志」场景下的差异，以及 `ThreadLocal` 必须在请求结束时清理的原因。

## 五、技术亮点展开（面试官追问时用）

### 1. 动态 SQL 的效率取舍

- 做法：`<where>` + `<if>`，首个条件不加 `and` 由 `<where>` 自动裁剪；`<set>` 让 update 只落非空字段。
- 为什么不用 `@Select` 注解拼字符串：可读性差、无法复用 `<sql>` 片段、条件一多就失控。
- 加分话术：所有参数一律 `#{}` 预编译，不用 `${}`，从根上避免 SQL 注入；`like` 用 `concat('%',#{name},'%')` 而不是在 Java 里拼 `%`。

### 2. 一对多的三种写法，为什么选嵌套 resultMap

| 方案 | 代价 |
| --- | --- |
| 先查主表，再循环查从表 | N+1，10 个员工 11 次查询 |
| 两次查询 + 内存分组 | 需要在 Service 里写聚合，代码分散 |
| 一次 JOIN + 嵌套 resultMap | 1 次查询，但结果集有冗余列（JOIN 放大） |

选第三种的理由：数据量在千级，JOIN 放大的网络开销远小于 N+1 的往返开销；且映射逻辑收敛在 XML 里。**如果是十万级，会改成两次查询 + 内存分组。**

### 3. ThreadLocal 的两个坑（能讲清这个很加分）

- 坑一：**请求结束必须 `remove()`**。Tomcat 线程复用，不清理会让下一个请求读到上一个用户的 ID。清理位置放在拦截器 `afterCompletion`，而不是业务代码里——业务可能抛异常，`finally` 写漏一处就漏。
- 坑二：**拦截器 `preHandle` 返回 `false` 时不走 `afterCompletion`**，所以「解析成功后再 set、set 之后才可能 return true」的顺序不能颠倒。
- 延伸问：异步/线程池场景 ThreadLocal 会丢，需要 `InheritableThreadLocal` 或手动透传（`TaskDecorator`）。

### 4. 事务传播：为什么审计日志要用 `REQUIRES_NEW`

- 同事务的后果：业务回滚 → 日志一起回滚 → 最需要的那条「失败记录」恰好没了。
- `REQUIRES_NEW` 会挂起当前事务、开新连接，所以**日志插入不随业务回滚**。
- 代价：占用第二个数据库连接，高并发下要评估连接池大小；且业务未提交时日志已落库，可能出现「日志有、业务无」的短暂不一致——审计场景可以接受。

### 5. AOP 记录日志的四个细节

1. 用 `AopUtils.getTargetClass()` 而不是 `joinPoint.getTarget().getClass()`，否则拿到 `DeptController$$EnhancerBySpringCGLIB`。
2. 过滤 `ServletRequest/ServletResponse/MultipartFile/BindingResult`，否则序列化直接抛异常。
3. 用独立的 `ObjectMapper` 并注册 `JavaTimeModule`，否则 `LocalDateTime` 序列化失败；`FAIL_ON_EMPTY_BEANS` 要关掉。
4. 截断到列长度，否则 `Data too long` 把日志写入搞崩；外层再包一层 try-catch，**日志永远不能影响主流程**。

## 六、项目难点（STAR 三段式，面试可直接讲）

### 难点一：跨表更新的数据一致性

- **S**：员工有基本信息和工作经历两张表，编辑时要先删旧经历再插新经历。
- **T**：保证「要么都成功，要么都不动」。
- **A**：审查时发现该 Service 方法只有 `@Transactional` 加在了 `save` 上，`update` 漏了；补上 `@Transactional(rollbackFor = Exception.class)`，并确认异常能穿透到代理边界（不能自己 catch 掉）。
- **R**：消除「提交失败但旧数据已被删」的永久性数据丢失。

### 难点二：审计日志与业务事务的耦合

- **S**：员工新增的日志写在 `finally` 里，与业务共用同一事务。
- **T**：业务失败时日志仍要保留。
- **A**：把日志 Service 的传播行为改为 `REQUIRES_NEW`，并确认 Spring 中「同类内部调用不走代理」的陷阱——日志方法必须放在另一个 Bean 里（本项目正是如此）才生效。
- **R**：失败操作也能被审计追溯。

### 难点三：接口暴露了不该暴露的字段

- **S**：员工列表用 `select e.*` 查，实体直接返回前端。
- **T**：不改变前端调用方式的前提下收敛敏感字段。
- **A**：短期用 `@JsonProperty(access = WRITE_ONLY)` 让密码可入不可出；长期引入 `EmpVO`，实体不出 Service 层。
- **R**：接口不再返回任何密码字段，同时保持前端零改动。

## 七、高频追问 & 答题要点

| 追问 | 要点 |
| --- | --- |
| 为什么用 JWT 不用 Session？ | JWT 无状态、天然支持多实例横向扩展；代价是无法主动失效、payload 不能放敏感信息、续期要靠双 token。本项目单机也选 JWT，主要是为了练无状态鉴权。 |
| token 存哪？ | 前端 `localStorage`，每次请求放自定义 header `token`；更规范是 `Authorization: Bearer`。`localStorage` 有 XSS 风险，`httpOnly` Cookie 有 CSRF 风险，二选一，看场景。 |
| token 过期了怎么办？ | 本项目固定 1 小时，过期返回 401 让前端跳登录。**不足**：没有刷新机制，用户体验差；改进是 access token（短）+ refresh token（长、存库可吊销）。 |
| 怎么退出登录？ | 目前没做，因为 JWT 无状态。要做得加 Redis 黑名单（存 `jti` 到过期时间）或缩短有效期。**这是主动暴露短板，面试官反而认可。** |
| PageHelper 原理？ | 基于 MyBatis 拦截器 `Interceptor`，在 `Executor.query` 前改 SQL 加 `limit`，并自动派生 `count` 语句；`startPage` 把分页参数存 ThreadLocal，所以**必须紧跟查询**，中间不能插别的查询。 |
| 深分页怎么优化？ | `limit 1000000,10` 会扫描前 100 万行。用游标/延迟关联：`where id > 上一页最大id order by id limit 10`，或先查主键再 JOIN 回表。 |
| 事务失效的常见场景？ | ① 同类内部 `this.` 调用不走代理；② 方法非 `public`；③ 异常被 catch 没抛出；④ 抛的是受检异常而默认只回滚 `RuntimeException`（所以写了 `rollbackFor = Exception.class`）；⑤ 数据库引擎不支持事务（MyISAM）。 |
| 为什么日志要 `REQUIRES_NEW`？ | 见上「难点二」。追问「连接池够吗」→ 需要评估，日志插入很快，但突发流量下会多占连接，可以考虑改为异步（`@Async` + 队列）。 |
| 有没有做参数校验？ | **诚实回答：原始版本没做，这是缺陷。** 已规划引入 `spring-boot-starter-validation` + `@Valid` + 全局 `MethodArgumentNotValidException` 处理。（如果你按文末建议补了，就直接讲怎么做的。） |
| 测试怎么写的？ | 原始版本只有一个空的 `contextLoads`，**这是弱点**。建议补完再写进简历：Mapper 层用 `@MybatisTest` 验动态 SQL，Controller 层用 `@WebMvcTest` + `MockMvc` 验 401 与异常分支。 |
| 密码为什么明文存？ | **不要辩解**。直接说「这是原项目的缺陷，我审查时发现了，已改为 BCrypt 加盐哈希」，然后把 `BCrypt.hashpw/checkpw` 的用法讲清楚。 |
| 有没有做权限控制？ | 原始版本只做了**认证**没做**授权**——任何登录用户都能删员工。改进方向：加角色字段 + `@PreAuthorize` 或拦截器按 URL 前缀校验。 |

## 十、Redis 优化（已落地的可写条目）

> 这一节是**真的改完了**（`mvn test` 通过，含 Spring 容器装配测试），可以直接写进简历。
> 设计细节与验证命令见 [Redis 优化方案](Redis优化方案.md)。

### 10.1 简历条目（3 行版，插到项目经历中）

- 引入 Redis 优化读多写少链路：对部门、班级、统计报表实施 Cache-Aside 缓存，针对缓存穿透（空值占位）、击穿（SETNX 互斥重建）、雪崩（TTL 随机抖动）分别设计防护，并以「先更库、再删缓存」保证写后一致性。
- 基于 Redis 补齐 JWT 的无状态短板：登录失败计数 + 账号锁定防暴破，登出时按 `jti` 写入黑名单（TTL 与 token 剩余有效期严格对齐，自动清理），配合 Lua 脚本实现登录/上传接口的原子限流。
- 将操作日志由同步写库改为 Redis List 队列异步批量落库，请求线程只做一次 LPUSH；设计「Redis 不可用 / 队列积压时自动退回同步写库」的降级路径，保证日志不丢。**全链路缓存操作 fail-open，Redis 故障不导致业务不可用。**

### 10.2 简历条目（完整版，拆成 5 条）

- **缓存设计**：识别出「部门/班级列表、统计报表」为读多写少且容忍延迟的数据，落地 Cache-Aside；分页查询**明确不缓存**（key 组合爆炸、命中率低），避免伪优化。
- **缓存三大问题**：用空值占位防穿透（60s 短 TTL）、`SETNX` 互斥锁防击穿（未抢到锁的线程限时等待 100ms 后重试，不阻塞线程池）、TTL 加 0~60s 抖动防雪崩。
- **JWT 主动失效**：为 token 增加 `jti` 并设计 Redis 黑名单，TTL 与 token 剩余有效期对齐实现自动清理；黑名单查询 fail-open，避免 Redis 抖动把全站用户踢下线。
- **原子性保障**：登录失败计数用 `INCR` + 首次设 `EXPIRE`（避免锁定期被无限顺延）；限流用 Lua 脚本把「自增 + 过期 + 判超限」合并为原子操作，规避两步之间进程崩溃导致的 key 永不过期。
- **异步化与降级**：操作日志改为 Redis List 队列 + `@Scheduled` 批量消费（`RPOP` 原子、天然支持多消费者），单条脏数据不影响整批、落库失败自动重推；队列读写异常或积压超阈值时退回同步写库。

### 10.3 追加的面试追问（Redis 专项）

| 追问 | 关键答法 |
|---|---|
| 为什么用 Redis 不用 Caffeine？ | 多实例下本地缓存互相看不见；单机纯读 Caffeine 更快，最佳实践是两级缓存。 |
| 怎么保证缓存和数据库一致？ | 先更库再删缓存；讲清「先删再更」的并发脏读场景；再给延迟双删 / Canal 订阅 binlog 作为进阶。 |
| 缓存击穿的锁为什么不用 `synchronized`？ | JVM 锁跨实例无效，必须用 Redis 的分布式锁（SETNX + TTL）。 |
| 你的降级是怎么做的？ | 每个 Redis 操作都包 safe 方法，异常返回中性值继续回源；再加一个 `app.cache.enabled` 总开关。要能说出**哪些地方 fail-open、哪些必须 fail-closed**。 |
| 固定窗口限流有什么问题？ | 边界突刺会放过 2 倍流量；改进是滑动窗口（ZSET）或令牌桶。 |
| List 队列会丢消息吗？ | 会——`RPOP` 后未落库时进程崩溃。**主动承认**，然后说 Stream + 消费组 + XACK 怎么解决。 |
| Redis 内存满了会怎样？ | 取决于 `maxmemory-policy`；这里要讲出「队列 key 不能被淘汰，所以用 `volatile-lru`（只淘汰带 TTL 的缓存 key）」。 |
| 为什么没用 `@Cacheable`？ | 空值缓存、互斥重建、TTL 抖动、降级都需自定义，封装 `CacheService` 更可控。 |

### 10.4 注意

- 写「优化了接口性能」时**别编数字**。如果没压测过，就说「把日志写入从请求链路中剥离」，不要写「RT 降低 40%」。
- 不要把这次改造说成「引入 Redis 支撑高并发」——项目里 Redis 的作用是**减少数据库压力 + 补安全短板**，不是扛 QPS。
- 如果面试官问「并发量多少」，诚实回答：个人项目没有真实流量，缓存收益是按「读多写少 + 聚合查询」的特性推导的。
